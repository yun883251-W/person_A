# 单进程有界并发

开发状态：已完成真实纯聊天突发压测。16 通道冷启动曾出现 MCP 重复启动超时；
改为服务级共享 MCP 后，16、32、64、128 路测试均全部成功，3 项离线生命周期回归通过。
128 路测试平均响应14.57秒、P95为16.72秒、健康接口最大延迟2.05秒。
这些结果不代表 RAG、规划、工具调用或持续负载具有相同容量。

## 执行结构

HTTP JSON 与 SSE 共用 RequestScheduler。专用 asyncio 循环调度已接受请求；
不同会话可进入不同工作通道，同一会话一次只派发一个请求，按提交顺序处理。
每个通道拥有独立 Agent 应用、SQLite 连接、会话缓存，数据库连接只在
所属工作线程使用。每次问答恢复会话，结束后释放会话缓存，下一轮从数据库恢复。

默认 HTTP 应用在服务启动时只创建一套 MCP 运行时，各通道借用连接、每轮刷新工具快照。
通道关闭或索引刷新不关闭共享 MCP；服务排空请求并关闭所有应用后统一释放。
MCP 启动失败会记录服务端异常并降级为空工具集，聊天和知识问答仍可执行；
修复工具配置后需重启服务恢复工具。CLI 和自定义应用工厂维持原来的资源所有权。

同步 Agent 通过模型网关将请求交给调度循环的 `ainvoke()`，共用 Semaphore。
意图、规划、回答、摘要、画像候选提取均经过同一 HTTP 模型额度；MCP 使用独立限额。
模型重试仍遵守原 provider 策略，每次实际调用重新申请名额。模型名额等待有超时，
请求网络超时沿用 CHAT 配置。CLI 沿用同步调用，不共享 HTTP 进程额度。

这是“协程调度和异步模型 I/O + 有界同步工作通道”的混合实现，不是整个 Agent 的
纯异步重写。模型等待时工作通道仍被占用，因此活动问答上限受通道数限制。
模型 API 允许 2500 并发不等于当前应用已经支持 2500 路问答；当前通道配置上限为128，
未做任何容量承诺。每个活动通道可能加载索引副本，需要评估内存；MCP 子进程不随通道数增加。
向量调用继续使用既有实现，仍可能成为瓶颈，本次未改造向量服务。

## 配置

以下设置写入自己的 `.env` 后重启生效；不要直接覆盖已有文件。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| API_SESSION_CONCURRENCY | 4 | 独立工作通道，1—128 |
| API_QUEUE_CAPACITY | 128 | 额外准入容量，1—10000 |
| API_QUEUE_TIMEOUT_SECONDS | 60 | 请求尚未派发的最长等待时间 |
| API_MODEL_CONCURRENCY | 8 | HTTP 进程所有模型调用的共享额度，1—2500 |
| API_MODEL_WAIT_SECONDS | 60 | 模型或 MCP 名额等待上限，不是网络调用超时 |
| API_MCP_CONCURRENCY | 2 | 本进程同时派发的 MCP 调用数，1—64 |

总准入上限为工作通道数 + 额外准入容量，包含执行和等待中的问答及管理请求。
同会话请求或管理屏障可能使通道暂时空闲，等待数量此时可占用整个准入容量。
调整模型额度不能突破活动通道上限。先小规模验证，再根据延迟、内存和错误率逐级调大。

仍必须使用 `uvicorn knowledge_agent.api:create_app --factory --workers 1`。
限流、会话顺序及管理屏障都是进程内实现，多 worker 或多个 API 实例操作同一数据库
不受同一锁保护。多个进程/CLI 共用 API 账号也不会自动共享模型额度。

## 排队、管理与关闭

- 同会话按序派发，等待同会话的任务不占工作通道；可以跳过它先运行其他会话。
- 删除、清空、修改记忆、知识库管理等操作作为全局独占屏障。排在屏障之后的请求
  等待它完成，避免问答执行期间删除会话或切换索引。知识库只读列表/预览目前也沿用该管理通路。
- 索引发布后的刷新回调会更新已初始化的通道；刷新失败的通道释放旧应用，后续重新加载。
- 画像候选提取不写会话，作为独立辅助请求并发调度。画像保存仍使用独立短连接和乐观版本检查。
- 会话只读查询独立使用最多4个读取线程，总在途读取上限128，不调用模型。
- 队列满返回503 `request_queue_full`；等待超时返回503 `request_queue_timeout`，过期任务不执行。
  SSE 已发响应头后通过 error 事件携带状态；排队期间仍发送心跳，不自动重试。
- HTTP 断开不取消已接受任务。用户应查看历史确认结果，不应因等待时间长直接重复发送。
- 停止服务后停止接收请求，等待已接受任务完成或排队过期，再关闭通道和资源。
  运行中任务遵循各自模型/MCP超时，没有新增强制取消语义。

管理屏障和同会话串行会牺牲部分吞吐量，以保持现有业务状态和外部工具行为。
MCP 超时后远端可能仍在收尾，限额只约束本地调用生命周期，不保证远端已停止。

## 观测与兼容

`GET /concurrency` 返回模式、通道数、running、waiting、outstanding、准入容量、
模型/MCP限额和是否接收请求，不暴露用户问题或会话ID。
默认运行时还返回 `mcp_startup_error` 与 `mcp_servers`，用于检查启动失败和各服务器状态。
`/health` 的 busy 表示有任务在途，不等于当前不能接收请求。
页面已有单条发送限制保留；后端并发可由多个页面或 API 客户端使用。
自定义 runtime 的 store/application 工厂默认保留旧串行模式；只有明确保证每次创建
独立对象时才传 `concurrent_sessions=True`。旧同步测试假模型不自动获得原生异步能力。

## 待执行回归与压测

1. 两个会话同时提交，均完成且历史/引用/测评状态互不混用。
2. 同一会话提交命名和追问，第二轮只能在第一轮保存后执行。
3. 活动问答期间提交删除、清空记忆、索引更新：等待屏障并保持持久化一致。
4. 小容量队列、同会话积压、管理屏障、队列超时：过期任务没有模型或工具副作用。
5. 假异步模型记录峰值调用数；意图/规划/回答/摘要/画像合计不突破模型限额。
6. MCP限额、服务异常、客户端断开及关闭时，不提前释放会话顺序或重复派发工具。
7. 观察索引副本、MCP子进程、SQLite写锁、内存和响应延迟，再决定通道数量。
8. 自定义串行运行时及 CLI 保持原行为；原有 JSON/SSE 错误映射兼容。
