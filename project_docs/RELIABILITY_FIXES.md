# 规划、检索与回答可靠性修复

本轮完成代码修改与源码审阅，遵守“只开发、不测试”：未运行测试、语法/导入检查、服务、浏览器或模型请求。下面描述实现及预期行为，不是验收结果。实际 `.env`、知识索引和会话数据未修改，不要求清空历史或重建索引。

## 问题处理

| 原编号 | 当前处理 | 边界 |
| --- | --- | --- |
| 1 依赖图随机 | 明确的 2～3 个任务由程序分句、编号、解析显式前置引用；不再向模型请求依赖图 | 模糊指代需澄清；这是一种有限规则规划，不是自由自主规划 |
| 2 资料不足混成执行失败 | 步骤、最终汇总、trace 与页面区分资料覆盖不足、校验失败及执行异常 | `partial_answer` 不等于整个知识库没有该主题，仍需检查召回内容 |
| 3 无引用拒答被丢弃 | 增加回答状态行；符合简短拒答格式的正文保留，拒答无需引用 | 状态自报不提供事实豁免；混合事实、未知引用、手写文件行号仍校验 |
| 4 检索必有 top-k | 原始候选先经过 cosine/主题匹配门槛，再 RRF 与 top-k；允许返回空结果 | 默认阈值未校准，不能保证所有库外问题都零召回 |
| 5 超范围却成功 | 明确识别超范围拒答；纯拒答移除引用和来源，混合事实拒答按状态冲突处理 | 旧会话结果不重算 |
| 6 B 站路由变化 | 核对现有“我想在B站看火影忍者”确定性规则路径并保留；规划子句复用同一授权入口 | 当前未复现该句随机路由；陌生表达仍有模型分类，不能承诺任意改写结果相同 |
| 7 冷启动慢 | 记录 Ollama Embedding 实际加载耗时与总耗时 | 未调整显存策略、预热或模型驻留；未确认或解决实际慢请求根因 |
| 8 请求错误丢原因 | 后端日志增加真实 HTTP 状态、异常类型、调用次数及清理后的错误摘要 | 不把所有 `model_request_invalid` 推断为 HTTP 4xx；具体历史原因仍不可追溯 |
| 9 规划结构错零重试 | 明确任务路径取消模型图输出，消除该路径因图 JSON 格式不合格而失败的来源 | 未新增自动重试或执行工具重试；现有有限预算继续适用 |
| 10 错误码混杂 | 保留浏览器语义分类的超时、预算、格式/服务错误；planning 记录 reason/source | 真实目标不明仍要求澄清；旧日志不回填 |

## 稳定计划与例子

以下是待统一验收的预期行为，均未执行：

| 输入/场景 | 预期 |
| --- | --- |
| 先解释文档分块的作用，再介绍 Embedding 的工作原理，最后比较向量检索和关键词检索 | P1/P2/P3 均无依赖；重复提问或改变历史不会改变依赖图；P2 资料不足时 P3 仍可执行，受共享预算约束 |

程序构造计划不消耗模型调用。回答、可选 Skill/意图分类和补查仍消耗预算，因此不能据此承诺整轮固定调用次数。执行结果不会触发模型重新规划。

## 检索门槛

`.env.example` 增加以下默认配置；实际 `.env` 未添加也使用这些默认值：

```dotenv
RETRIEVAL_MIN_COSINE=0.45
RETRIEVAL_SEMANTIC_MIN_COSINE=0.65
RETRIEVAL_MIN_TOPIC_COVERAGE=0.6
```

接受较高 cosine 的语义候选、达到基础 cosine 且有足够主题匹配的候选，或完整主题匹配的关键词候选。主题匹配去掉通用提问词，中文使用连续双字，技术词保留 `C++` 等符号；多轮包装优先使用当前问题的主题。RRF 仅用于排序，不用作相关性概率。

这些默认值是启发式，后续需要用实际模型及问答样本校准，可能误召回或误过滤。相关性通过也不等于资料足够回答问题，回答阶段仍检查引用及不足声明。

`retrieve()` 维持旧返回类型；新增 `retrieve_with_diagnostics()` 同时返回同一索引快照的结果、版本和统计。检索工具携带候选数、通过数、最高 cosine/主题覆盖和生效阈值；原因分别为 `retrieval_relevant`、`retrieval_below_relevance`、`retrieval_no_candidates`。Embedding 或索引异常仍作为服务异常，不伪装成正常空检索。

## 回答协议与展示

知识回答提示词要求首行：

```text
ANSWER_STATUS: supported
这里开始写正文。
```

可选值为 `supported`、`partial`、`insufficient_evidence`、`needs_clarification`、`out_of_scope`。程序去掉状态行，再生成页面答案和历史上下文；MCP 回答不使用此协议。兼容未携带状态行的旧式回答，但仍执行同样校验。

状态行不是事实正确性的证明。只有短且全部由拒答、澄清或服务范围说明组成的正文可免引用；实质回答仍必须使用本轮已注册的 `[S编号]`。未知来源与手写文件名/行号继续拒绝。拒答附带合法来源标记时去掉标记并返回空来源列表，避免给无关文档背书。格式或状态冲突分别记录 `answer_contract_invalid`、`answer_status_conflict`。

页面与计划汇总分别显示“资料覆盖不足”“回答校验未通过”“执行异常”“需要补充信息”“超出范围”“已跳过”。纯拒答或证据不足不再被记录为调用失败。状态识别使用约定格式及保守语言规则，不能视为通用语义或事实蕴含验证器。

## 后端模型诊断

`knowledge_agent.models` logger 在 WARNING 记录 `chat_model_failure`：客户端类、原始异常类、真实 HTTP 状态或空值、标准化错误类别、是否可重试、当前 attempt 和最多 640 字符的错误摘要。摘要清理常见密钥、令牌、URL、请求载荷等信息，不发送到页面，不改变现有重试策略。日志仍应按后端运维数据管理。

同一 logger 在 INFO 记录 `embedding_timing` 的 `load_ms`、`total_ms`，来自 Ollama 响应中的纳秒字段；响应未提供时不编造数值。启用该 logger 的 INFO 输出并配置对应 handler 后可观察；单独设置 Uvicorn 的日志级别不一定配置应用 logger。没有新增预热请求、额外模型调用或自动改写显存参数。

代码部署后需重启后端、刷新页面才加载新逻辑；本轮没有代为启动。冷启动性能、阈值校准、不同模型遵循状态协议的效果，以及上述正反例，均留待用户安排统一验证。
